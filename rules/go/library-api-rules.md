# 库设计与 API 规范（Library & API Rules · L2）

> 定位说明：
> 本文件是 **L2 级规则**，用于定义本项目作为“通用工具库”的 API 设计标准与架构决策。
>
> ❌ 本文件不包含具体语法细节
> ✅ 本文件用于 **确保 API 设计的一致性与易用性**

---

## 1. 库定位与形态

本项目是一个 **通用工具库**，其主要形态为独立的功能 package。

### 设计原则
* **无侵入性**：尽可能减少对调用方代码结构的侵入。
* **零配置启动**：提供合理的默认配置，支持快速上手。
* **按需引用**：包之间应当低耦合，允许用户只引用需要的部分。

---

## 2. API 设计规范

### 2.1 构造函数与 Functional Options
* **必须** 优先使用 `NewXXX(opts ...Option)` 模式来处理可选配置。
* **默认配置**：必须在构造函数中通过 `DefaultOptions()` 初始化。
* **示例**：
  ```go
  func NewClient(opts ...Option) *Client {
      o := DefaultOptions()
      for _, opt := range opts {
          opt(o)
      }
      // ...
  }
  ```

### 2.2 接口暴露 (Interface)
* **生产者返回结构体，消费者定义接口**：API 应当尽可能返回具体的结构体或指针，以便扩展。
* **最小接口原则**：如果需要暴露接口，应保持接口方法尽可能少。

### 2.3 链式调用 (Fluent API)
* 对于简单的工具辅助类（如 `regexputil`），允许使用链式调用提高代码可读性。

---

## 3. 错误处理哲学

### 3.1 预定义错误 (Sentinel Errors)
* 所有的业务错误或逻辑错误应在 package 内预定义，以便调用方使用 `errors.Is` 判断。
* 错误命名格式：`ErrXXXX`（如 `ErrNotFound`）。

### 3.2 错误包装
* 在返回底层驱动（如 mongo, bbolt）的错误时，必须使用 `%w` 进行包装，并增加包级上下文。

### 3.3 参数校验
* 对于 API 的入口参数，必须进行严格校验。
* 校验失败应通过 `logger.InvalidParam` 记录日志并返回错误。

---

## 4. 依赖管理

### 4.1 最小化外部依赖
* core 逻辑尽可能减少对第三方库的依赖。
* 如果必须引用，应确保该库是社区主流且高性能的（如 `zap`, `sonic`）。

### 4.2 避免循环引用
* 严格禁止 package 之间的循环引用。
* 共享类型应提取到更底层或独立的 `types` / `errs` 包中。

---

## 5. 并发与资源管理

### 5.1 并发安全
* **默认不安全，显式声明安全**：除非包定义就是为了并发场景（如 `task`），否则默认不保证 goroutine 安全，需由调用方加锁。
* 如果包内部启动了 goroutine，必须提供 `Close()` 或 `Shutdown(ctx)` 方法来优雅释放资源。

### 5.2 内存管理
* 在处理大量切片或 `[]byte` 时，必须考虑使用 `sync.Pool` 进行复用。

---

## 6. 禁止行为 (Redlines)

* ❌ **禁止在包内直接调用 `os.Exit` 或 `panic`** (除非是不可恢复的核心初始化失败)。
* ❌ **禁止在库代码中使用标准库 `log`**，必须使用项目封装的 `logger`。
* ❌ **禁止硬编码配置路径**，所有外部参数应通过 Option 传递。

---

**本文件的唯一使命：**

> **让 library 的使用者感觉到 API 调用如同标准库般自然且一致。**
